WHAT THIS IMAGE IS
------------------
Second image containing the on-FPGA DSP chain (ENABLE_DSP_AVERAGE => true):

    seq_adder x2 (per-channel coherent sum, N = 4096)
        -> complex_div (ONE divide per step, sum(RX1)/sum(RX2))
        -> sample_fifo_51
        -> read-side mux selected by dsp_path_en (config GPIO bit 6)

The 1/N of a mean cancels in the ratio, so the sums are divided directly and no
mean is ever computed.

WHAT CHANGED SINCE v1 (hostedxA9.rbf, 13:00 build -- DO NOT USE THAT ONE)
------------------------------------------------------------------------
1. THE RAW PATH IS NO LONGER DESTROYED BY THE GENERIC.

   The ENABLE_DSP_AVERAGE generate branch used to end with

       fw_streams  <= (others => ZERO_SAMPLE);
       fw_controls <= (others => SAMPLE_CONTROL_DISABLE);
       fw_packet   <= PACKET_CONTROL_DEFAULT;

   intending to keep the stock FIFO "quiescent". That starved fifo_writer, so
   the stock 8192-word FIFO was never written. Since nothing sets dsp_path_en,
   the read mux sat on a FIFO that could never fill, and EVERY RX transfer timed
   out -- with the DSP path not even selected. Observed on hardware as:

       [ERROR] Transfer timed out for RX buffer ...
       [bladerf] RX dual error: Operation timed out

   fw_streams/fw_controls/fw_packet are now driven unconditionally from
   mux_streams/adc_controls/packet_control. The generic may only ADD a second
   path, never remove the first.

2. Shared valid for the two accumulators (carried over from the 13:00 build):

       dsp_sample_v <= mux_streams(0).data_v and mux_streams(1).data_v;

   Previously each accumulator ran off its own per-channel valid while
   complex_div was started by RX1 alone. If RX2 fell behind, the divide used
   RX2's HELD sum from a PREVIOUS step and reported it with div_by_zero clear.
   dsp_valid_skew_tb case 2: truth 98304, reported 49152 -- wrong by 2x,
   unflagged.

REMAINING PROBLEMS
------------------
1. TIMING IS STILL NEGATIVE, though much closer than the 13:00 build:

                                   13:00 build   this build
       AD9361 rx clock, 85C          -0.310        -0.081
       AD9361 rx clock,  0C          -0.828        -0.632

   rx_clock is an alias of ad9361.clock, so complex_div, both seq_adders and the
   DSP FIFO write side sit in the failing domain. That clock closed at +0.096 ns
   on 2026-09-05 with none of this logic present.

   This is combinational depth, not capacity -- 7% of the device is used. The
   fix is pipelining, and the failing path has not yet been identified with
   report_timing.

   Practical consequence: intermittent, temperature-dependent corruption on the
   capture path, worse cold than hot. Fine for bring-up, not for measurements
   you intend to trust.

2. THE DSP PATH STILL CANNOT DELIVER (dsp_path_en = 1).

   fx3_gpif.vhd:270-273:
       packet_enable = '1'  ->  rx_fifo_enough <= rx_meta_fifo_empty = '0'
       packet_enable = '0'  ->  (rx_fifo_full & rx_fifo_usedw) >= gpif_buf_size

   The DSP route bypasses fifo_writer, so nothing writes the meta FIFO and
   packet mode never bursts. In non-packet mode gpif_buf_size is 2048 while the
   DSP FIFO holds at most 51 words (102 read-side); the concatenated full flag
   satisfies the comparison anyway, and fx3_gpif has no underflow check during a
   burst (rx_fifo_empty is an input port never referenced in the state machine),
   so it would over-read by ~1946 words.

   Needs either meta-FIFO writes on the DSP path, or the results routed back
   through fifo_writer's packet port.

3. No host API yet for the NIOS SFCW sweep commands (SWPR/SWEP/SWST/SWQG).

USAGE
-----
    bladeRF-cli -l hostedxA9_niosIIf_sweep_dsp_v2.rbf

Loads volatile; a power cycle reverts to whatever is in flash. Do not -L this
image while timing is negative.

With dsp_path_en left at 0 (the default) this behaves as a normal bladeRF and
the Pi continues to do the averaging and division itself.
